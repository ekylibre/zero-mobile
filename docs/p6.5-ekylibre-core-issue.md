# [API v2] `POST /api/v2/interventions` n'est pas idempotent sur `provider.id` (+ `provider` non sérialisé en lecture)

> Draft d'issue à destination de l'équipe Ekylibre core (backend Rails / API v2).
> Source : validation dev local de l'app mobile `zero-mobile`, 2026-05-30.
> Copier-coller dans le dépôt `ekylibre/ekylibre` (ajuster labels/assignees).

## Résumé

L'app mobile `zero-mobile` (saisie offline → sync) envoie chaque intervention
en `POST /api/v2/interventions` avec un identifiant client stable dans le bloc
`provider` (`provider.id` = UUIDv4 généré une seule fois au moment de la
saisie, cf. ADR-13 côté mobile). L'objectif : permettre au **serveur** de
dédupliquer si le client renvoie le même POST (cas « ack réseau perdu après un
POST réussi »).

**Constat : le serveur ne déduplique pas.** Deux POST strictement identiques
(même `provider.id`) créent **deux interventions distinctes**. De plus, le
bloc `provider` **n'est pas relu** par l'API (ni dans la list, ni — semble-t-il
— exploitable en filtre), ce qui empêche aussi tout contournement côté client.

Sans correction, un farmer hors-ligne dont le téléphone perd l'ACK d'un POST
réussi verra l'intervention **dupliquée** au cycle de sync suivant. C'est un
**blocker pour la mise en pilote** de l'app mobile.

## Environnement

- Instance testée : Ekylibre demo (jeu de données de démo standard).
- API : v2, auth `simple-token`.
- Date du test : 2026-05-30.

## Étapes de reproduction

> Pré-requis : `EKY_URL`, `EKY_EMAIL`, `EKY_PASSWORD` exportés. Aucune donnée
> sensible dans ce ticket.

```bash
BASE="${EKY_URL%/}"
TOKEN=$(curl -fsS -X POST "$BASE/api/v2/tokens" \
  -H 'Content-Type: application/json' \
  -d "{\"email\":\"$EKY_EMAIL\",\"password\":\"$EKY_PASSWORD\"}" \
  | python3 -c 'import json,sys;print(json.load(sys.stdin)["token"])')
AUTH="Authorization: simple-token $EKY_EMAIL $TOKEN"

# UUID client figé, RÉUTILISÉ pour les deux POST
PID=$(python3 -c 'import uuid;print(uuid.uuid4())')

read -r -d '' BODY <<JSON
{
  "procedure_name": "spraying",
  "actions": [],
  "provider": { "vendor": "ekylibre-mobile", "name": "zero-mobile", "id": "$PID" },
  "working_periods_attributes": [
    { "started_at": "2017-03-09T10:00:00Z", "stopped_at": "2017-03-09T16:00:00Z" }
  ],
  "doers_attributes":   [ { "product_id": 292, "reference_name": "driver" } ],
  "targets_attributes": [ { "product_id": 7,   "reference_name": "cultivation" } ],
  "tools_attributes":   [ { "product_id": 246, "reference_name": "tractor" } ],
  "inputs_attributes":  [ {
    "product_id": 333, "reference_name": "plant_medicine",
    "quantity_value": 1.4, "quantity_handler": "volume_area_density",
    "quantity_unit": "liter_per_hectare"
  } ]
}
JSON

# POST #1
curl -s -X POST -H "$AUTH" -H 'Content-Type: application/json' -d "$BODY" \
  "$BASE/api/v2/interventions"      # => {"id":46}

# POST #2 — STRICTEMENT IDENTIQUE, même provider.id
curl -s -X POST -H "$AUTH" -H 'Content-Type: application/json' -d "$BODY" \
  "$BASE/api/v2/interventions"      # => {"id":47}  ← id DIFFÉRENT = doublon
```

## Comportement observé

- POST #1 → `201 {"id":46}`
- POST #2 (même `provider.id`) → `201 {"id":47}` — **nouvel id, doublon créé**.
- Reproduit deux fois (ids 44≠45, puis 46≠47).
- `GET /api/v2/interventions` ne renvoie **aucun champ `provider`** sur les
  interventions créées (ni sur les interventions de démo). Impossible donc,
  côté client, de vérifier « cet UUID a-t-il déjà été posté ? » :
  - pas de `provider` dans la réponse list/show ;
  - pas de filtre `?provider_id=` (seuls `modified_since` et `user_email`
    semblent supportés).

## Comportement attendu

1. **Idempotence au POST** : si une intervention existe déjà avec le même
   `provider.vendor` + `provider.id`, le serveur **ne crée pas de doublon**
   et renvoie l'intervention existante (`200` avec le même `id`, ou `201`
   no-op équivalent).
2. **Provider relisible** : le bloc `provider` (au moins `vendor` + `id`) est
   **sérialisé** dans `GET /api/v2/interventions` et `GET .../{id}`, et
   idéalement **filtrable** (`?provider_id=<uuid>` ou
   `?provider[id]=<uuid>`), pour permettre réconciliation et debug.

## Impact

- **Bloquant** pour le pilote de l'app mobile : duplication silencieuse des
  interventions sur un simple aléa réseau (très fréquent en conditions de
  terrain / zones blanches).
- Le garde-fou côté mobile (lock anti-réentrance UI) **ne couvre pas** ce cas :
  il empêche le double-tap, pas le re-POST au cycle suivant après un ACK perdu.
- Toute stratégie de contournement 100 % client est **impossible** tant que
  `provider` n'est ni relu ni filtrable.

## Correctif proposé (par ordre de préférence)

1. **Dédup serveur sur `provider` (recommandé).** À la création, si
   `(provider.vendor, provider.id)` existe déjà → renvoyer l'existant au lieu
   de créer. Implémentable via un index unique partiel sur le provider, ou un
   `find_or_create_by` en amont du builder d'intervention. **+** sérialiser
   `provider` dans les réponses de lecture. Règle la cause racine et bénéficie
   à tout futur mécanisme de pull/merge mobile.
2. **A minima** : exposer `provider` en lecture **et** un filtre
   `?provider_id=`. Permet à l'app de faire un GET défensif avant POST
   (latence ×2, course réseau résiduelle, mais débloque le pilote).

## Critères d'acceptation

- [ ] Deux POST identiques avec le même `provider.id` → **une seule**
      intervention ; le 2ᵉ renvoie le même `id` que le 1ᵉʳ.
- [ ] `GET /api/v2/interventions` (et `.../{id}`) renvoient le bloc `provider`
      (`vendor`, `name`, `id`, `data`).
- [ ] (Si option 2) `GET /api/v2/interventions?provider_id=<uuid>` filtre
      correctement.
- [ ] Le `data` du provider (`app_version`, `os`, `locale`) est conservé tel
      quel (utile pour le triage des bugs pilote).

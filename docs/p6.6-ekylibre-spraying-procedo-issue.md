# [API v2] `POST /api/v2/interventions` (spraying) — l'interpréteur Procedo ne sait pas évaluer `ActorPresenceTest` / `Division`

> Draft d'issue à destination de l'équipe Ekylibre core (backend Rails / API v2).
> Source : validation dev local de l'app mobile `zero-mobile`, 2026-05-30.
> Copier-coller dans le dépôt `ekylibre/ekylibre` (ajuster labels/assignees).
> Ticket frère de `p6.6` ↔ `p6.5` (idempotence `provider.id`).

## Résumé

L'app mobile `zero-mobile` POST une intervention **spraying** complète
(`procedure_name: "spraying"` + working_period + doer + **target** + **input**)
sur `POST /api/v2/interventions`. Dès que le payload contient une
`targets_attributes` **ou** une `inputs_attributes`, le serveur répond **400**
avec une erreur de l'**interpréteur de formules Procedo** :

```json
{ "errors": ["Dont known how to manage node: Procedo::Formula::Nodes::ActorPresenceTest"] }
```

```json
{ "errors": ["Dont known how to manage node: Procedo::Formula::Nodes::Division"] }
```

Une pulvérisation a **par définition** une parcelle cible et un intrant phyto :
le payload nominal de l'app **ne peut donc jamais aboutir**. C'est un **blocker
fonctionnel** pour la synchronisation des interventions spraying (cœur du v1).

Le `reference_name` du tool (`sprayer`, `tractor`, ou tool absent) **n'a aucun
impact** : l'erreur vient de l'évaluation des formules de la procédure, pas des
acteurs fournis.

## Environnement

- Instance testée : Ekylibre demo (jeu de données de démo standard), via tunnel
  ngrok vers le `docker compose` local.
- API : v2, auth `simple-token`.
- Date du test : 2026-05-30.

## ⚠️ Régression possible (à vérifier en priorité)

Le **même POST** (avec `targets_attributes` + `tools_attributes`) renvoyait
**`201`** plus tôt le 2026-05-30 (cf. `p6.5-ekylibre-core-issue.md`, repro lignes
56/77, interventions créées ids 46/47). Quelques heures plus tard, le même appel
renvoie **`400`**. Si l'instance n'a pas été modifiée volontairement côté app,
c'est une **régression serveur** (mise à jour du core, re-seed, ou changement de
définition de la procédure `spraying`) à investiguer.

## Étapes de reproduction

> Pré-requis : `EKY_URL`, `EKY_EMAIL`, `EKY_PASSWORD` exportés.

```bash
BASE="${EKY_URL%/}"
TOKEN=$(curl -fsS -X POST "$BASE/api/v2/tokens" \
  -H 'Content-Type: application/json' \
  -d "{\"email\":\"$EKY_EMAIL\",\"password\":\"$EKY_PASSWORD\"}" \
  | python3 -c 'import json,sys;print(json.load(sys.stdin)["token"])')
AUTH="Authorization: simple-token $EKY_EMAIL $TOKEN"

post() { # $1 = attributs supplémentaires
  PID=$(python3 -c 'import uuid;print(uuid.uuid4())')
  curl -s -o /tmp/r.json -w "HTTP %{http_code} -> " -X POST -H "$AUTH" \
    -H 'Content-Type: application/json' \
    -d "{\"procedure_name\":\"spraying\",\"actions\":[],\
\"provider\":{\"vendor\":\"ekylibre-mobile\",\"name\":\"zero-mobile\",\"id\":\"$PID\"},\
\"working_periods_attributes\":[{\"started_at\":\"2017-03-09T10:00:00Z\",\"stopped_at\":\"2017-03-09T16:00:00Z\"}],\
\"doers_attributes\":[{\"product_id\":292,\"reference_name\":\"driver\"}]$1}" \
    "$BASE/api/v2/interventions"; cat /tmp/r.json; echo
}

post ''                                                                                     # minimal
post ',"targets_attributes":[{"product_id":7,"reference_name":"cultivation"}]'              # + target
post ',"inputs_attributes":[{"product_id":333,"reference_name":"plant_medicine","quantity_value":1.4,"quantity_handler":"volume_area_density","quantity_unit":"liter_per_hectare"}]'  # + input
```

## Comportement observé

| Payload                                    | Résultat                                                                                       |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| minimal (proc + working_period + doer)     | `201 {"id":48}` ✅                                                                             |
| + `targets_attributes` (cultivation)       | `400 {"errors":["Dont known how to manage node: Procedo::Formula::Nodes::ActorPresenceTest"]}` |
| + `inputs_attributes` (plant_medicine)     | `400 {"errors":["Dont known how to manage node: Procedo::Formula::Nodes::Division"]}`          |
| + target + input (= payload réel de l'app) | `400 … ActorPresenceTest`                                                                      |
| `actions: ["spraying"]` (au lieu de `[]`)  | `403 {"errors":["Actions est invalide"]}`                                                      |

Constats :

- L'erreur est levée par l'évaluation d'une **formule de la procédure
  `spraying`** lors du calcul/validation de l'intervention, pas par la
  désérialisation du payload.
- Le message `Dont known how to manage node` est une **exception interne**
  (faute de frappe « Dont known » incluse) — un type de nœud Procedo
  (`ActorPresenceTest`, `Division`) n'est pas géré par l'interpréteur sollicité
  par le chemin API v2.
- Statut HTTP **400** pour ce qui est en réalité une **erreur interne**
  (500-like) côté serveur — voir aussi la note de `p6.5` sur le
  `undefined method 'unit' for nil:NilClass` (même famille).

## Comportement attendu

1. Un `POST /api/v2/interventions` pour une procédure `spraying` avec
   `targets_attributes` + `inputs_attributes` valides **crée l'intervention**
   (`201`), en évaluant correctement les formules de la procédure
   (`ActorPresenceTest`, `Division`, etc.).
2. À défaut, si une combinaison est réellement invalide, renvoyer un **message
   de validation métier explicite** (et non une exception d'interpréteur), avec
   un statut cohérent.

## Hypothèses / pistes (côté core)

- L'interpréteur Procedo utilisé par le builder d'intervention **API v2** est
  un sous-ensemble de celui utilisé par le web : certains nœuds
  (`ActorPresenceTest`, `Division`) ne sont pas implémentés sur ce chemin.
- Ou bien la **définition XML de la procédure `spraying`** a évolué et introduit
  des nœuds non supportés par l'interpréteur API.

## Impact

- **Bloquant** : aucune intervention spraying (la seule procédure du v1 mobile)
  ne peut être synchronisée tant que ce n'est pas corrigé.
- Indépendant de l'idempotence (`p6.5`) : ici le POST échoue avant toute
  création, donc pas de doublon — mais flux totalement bloqué.

## Critères d'acceptation

- [ ] Le POST « payload réel app » (proc + wp + doer + target cultivation +
      input plant_medicine) renvoie `201` et crée l'intervention.
- [ ] Les nœuds `ActorPresenceTest` et `Division` sont évalués sans exception
      sur le chemin API v2 (ou la procédure n'en dépend plus).
- [ ] Une combinaison réellement invalide renvoie un message de **validation
      métier** (pas `Dont known how to manage node`), avec un statut adapté.

## Côté app mobile (déjà fait, pour info)

- L'app traite désormais un `400` comme une **erreur de validation définitive**
  (pas de retry en boucle) et **affiche le message serveur** (`errors[]`) dans
  l'écran détail de l'intervention. Cf. CHANGELOG _Unreleased — Fix gestion 400_.
- Le payload mobile est jugé correct ; aucun contournement client n'est
  possible (le contenu minimal qui passe — sans target ni input — n'a pas de
  sens métier pour une pulvérisation).
